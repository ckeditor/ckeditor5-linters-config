The `no-shadow-unsafe-dom-apis` rule now reports reading `relatedTarget`, points at the shadow-aware helper that replaces each reported API (`isConnected` or `containsNode()` for `contains()`, `getParentNode()` and `getParentElement()` for `.parentNode` and `.parentElement`), and no longer asks for a `{ shadowRoots }` option in `caretRangeFromPoint()` calls made on a document that is not spelled as a global one, such as `domDoc.caretRangeFromPoint( x, y )`.

`relatedTarget` is retargeted at Shadow DOM boundaries, so it does not point at the actual node the pointer came from or went to. It is reported on every access, without checking what object it belongs to, since a name this specific is rarely used for anything else and the occasional false positive can be silenced with an ESLint disable comment. Destructuring, for example `const { relatedTarget } = evt`, is not covered.

Native `caretRangeFromPoint()` takes coordinates only and ignores any further argument, so the option could never make such a call shadow-aware. These calls are now recognized by the method name alone and reported as unsupported no matter what object they are called on, while `caretPositionFromPoint()`, which does accept the option, is still reported for missing it.
