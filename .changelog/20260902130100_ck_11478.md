The `no-shadow-unsafe-dom-apis` rule now reports reading `relatedTarget`, points at the shadow-aware helper that replaces each reported API (`isConnected` or `containsNode()` for `contains()`, `getParentNode()` and `getParentElement()` for `.parentNode` and `.parentElement`), and no longer reports `caretRangeFromPoint()` calls at all.

`relatedTarget` is retargeted at Shadow DOM boundaries, so it does not point at the actual node the pointer came from or went to. It is reported on every access, without checking what object it belongs to, since a name this specific is rarely used for anything else and the occasional false positive can be silenced with an ESLint disable comment. Destructuring, for example `const { relatedTarget } = evt`, is not covered.

Legacy `caretRangeFromPoint()` accepts coordinates only and has no shadow-aware form, so it is used exactly where `caretPositionFromPoint()` is unavailable. There is nothing to switch to and no option to add, so flagging it only produced noise in the fallback branch. Only `caretPositionFromPoint()` is still reported when it is missing a `{ shadowRoots }` option.
